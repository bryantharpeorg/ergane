# 032 re-scope note — 2026-08-12 evening (operator)

## Why this spec is parked at draft

The premise of US1 — "the epic's command-emission order varies with wakeup
order; fix it in `factory/workgraph/workflow.py`" — is contradicted by the
evidence gathered on 2026-08-12. Full chain on the findings ledger under
`interpreter/replay-test-nondeterminism-under-load` (recurrences 3–5). The
short version:

1. **The error string's direction was pinned empirically.** Mutating a
   healthy recorded history's first `teardown_attempt` schedule into
   `validate_target_repo` reproduces the incident's exact `[TMPRL1100]`
   message. "Scheduled event" = what history holds; "activity command" = what
   replay emitted. The incident therefore requires the *recorded history* to
   carry a phantom second `validate_target_repo` at a teardown position.
2. **The workflow emits `validate_target_repo` exactly once**, before any
   node dispatches, and was audited clean on every nondeterminism axis:
   no unordered iteration feeding command emission, no `asyncio.gather/wait`,
   `wait_condition` waiters resolve in registration order, and a cap=1
   history has one command per activation — nothing for wakeup order to
   reorder.
3. **Exhaustive local forcing never reproduced it** (six axes: 100-seed
   completion delays; no-sticky worker; CPU starvation; injected
   workflow-task timeouts + deadlock failures at every activation position;
   3-wide stall windows combined with delayed completions; all verified to
   put real TIMED_OUT/FAILED workflow tasks into history). All replay green.
4. **The load coupling is explained**: the Java time-skipping test server
   records every `epic_status` query as a real workflow-task block (77 vs 60
   blocks under query pressure; the harness queries every 50 ms), so the
   recorded history's structure is wall-clock-dependent. Under runner load,
   a mis-sliced history hand-off lets the worker re-execute from the top and
   the server accept a duplicate command into the record.

## Replacement story shape (for re-scoping, not yet authored)

One small, test-only story — no `factory/` production change:

- Pin `fetch_history()` to the run actually started (`result_run_id`), so an
  orphaned server or reused workflow id cannot serve a stranger's history.
- Replay under the same runner that recorded (`UnsandboxedWorkflowRunner`),
  so record and replay execute the same class object.
- Drop the mid-attempt `epic_status` query from the fake agent for this test
  (it exists for concurrency assertions this test does not make).
- Keep the one-`validate_target_repo` history assertion as a standing
  tripwire ahead of the replay, and the dump-on-failure capture so any
  recurrence self-documents.
- Convert the two direct `EpicWorkflow` class patches in the test file to
  `monkeypatch.setattr` (audit hygiene item; unrelated to this bug but the
  same failure family).

Amplifiers worth their own eventual story (from the audit, not blocking):
`_cancel()` swallows `asyncio.CancelledError` (workflow.py ~1655), which can
wedge evictions; command emission inside `finally` blocks slows eviction
(the SDK blocks the command leak, but eviction liveness suffers).

## 2026-08-13 capture night — diagnosis superseded AGAIN, now with fixtures

The confirmation run happened, involuntarily: 026/us1's PR (#45) failed the
required check three consecutive times with the incident signature, and a
capture branch built from its tree (draft PR #46, never merge) reproduced
**10-for-10 on pull_request runs and 6-of-10 on push runs**, dumping every
recorded history as an artifact.

What the captures prove:

1. **The phantom/corrupted-history hypothesis is dead**: the discriminator
   passed in every dump — each recorded history holds exactly one
   `validate_target_repo`, well-formed, 356 events.
2. **The divergence is replay-side and environment-conditioned**: every
   captured history replays CLEAN locally under both Python 3.13 and 3.12.
   Only on loaded CI runners, mid-full-suite, does replay emit
   `teardown_attempt` against the first scheduled event.
3. **The mechanism candidate is the audit's own amplifier pair, promoted to
   cause**: the CI failure logs carry `RuntimeError: coroutine ignored
   GeneratorExit` beside every TMPRL1100. Under load the deadlock detector
   (2s) evicts the workflow mid-activation; `_cancel()` swallows the
   cancellation (workflow.py ~1655, "coroutine ignored GeneratorExit" is that
   swallow, verbatim), and teardown command emission living in `finally`
   blocks leaks a `teardown_attempt` command into the replay command stream.
   TMPRL1100 is the symptom, not the disease.

Consequences: the replacement story is NOT test-only after all — the fix is
the small production pair the audit scoped (un-swallow `CancelledError`; move
command emission out of eviction-path `finally`), plus the test hardening
above. Ten history fixtures live in the repro-history artifacts of run
31667012586; the capture tree (PR #46) is a standing regression bench.
Drafted as specs/038-replay-eviction-leak.
