# 078-US1 evidence — SC-001, SC-002, SC-003

Every run below was performed in this worktree on 2026-08-21/22 and pasted, not

## The question this story turned out to be about

The plan expected no host to have a `gh` old enough to refuse `baseRefOid`, and
told this node to fake the refusal if so (trap 10). It did not have to. **The
`gh` this node's environment resolves is 2.45.0 and really does refuse it** —
which turned the interesting question from "how do I stage a refusal" into "who
is wrong when a refusal happens", and that has two different answers.

```
$ command -v gh; gh --version
/usr/bin/gh
gh version 2.45.0 (2026-03-17 Ubuntu 2.45.0-1ubuntu0.3+esm3)
$ echo $PATH
/home/admin/.local/bin:/home/admin/.nvm/versions/node/v22.22.2/bin:/usr/bin
$ ls /home/admin/.local/bin/gh
ls: cannot access '/home/admin/.local/bin/gh': No such file or directory
```

The first attempt at this story read that as the tree being broken and left the
gate red on two tests. **It was wrong**, and the operator supplied the
measurement that could not be made from inside this environment:

> `/usr/bin/gh` on this host really is 2.45.0 (Ubuntu ESM). But the worker's
> PATH resolves `/home/admin/.local/bin/gh` 2.98.0 first, and that is what
> `poll_landing` actually shells out to — verified live today: three landings
> (PRs #268, #269, #270) polled `baseRefOid` successfully this afternoon […]
> Your attempt runs with a per-node `HOME` and a `PATH` without
> `/home/admin/.local/bin`, which is why you can only see 2.45.0.
>
> — operator, 2026-08-21, answering this node's question

So there are two `gh` binaries on one machine, both real, giving two true and
opposite answers about the same well-formed argv. A check that fails on one of
them is not measuring the tree; it is measuring whose `PATH` ran it. The
operator's instruction was to make the check honest about that instead:

> validate `_VIEW_FIELDS` against what the locally resolved `gh` declares at
> runtime, and treat a locally-undeclared field exactly the way this spec treats
> it at runtime — deny on nonzero exit, degrade explicitly — so the same suite
> is green on a 2.45.0 host and a 2.98.0 host without shrinking `_VIEW_FIELDS`
> and without pinning any version into a test. `gh`'s version is a property of
> the environment, not of the code; hardcoding 2.98.0 into a check re-creates
> the defect this story removes.

That is what is built. `_gh_would_refuse` denies exactly as strictly as before —
it is the *classifier* and it never softened. What changed is that the two tests
which run the real tree's argvs now ask a second question after a refusal:
**is this argv malformed, or is this machine behind the tree?**

## Which refusals are excused, and why that is not a hole

The dangerous version of "degrade on a field the local `gh` lacks" excuses
*every* such field — and a typo in `_VIEW_FIELDS` is indistinguishable from a
version gap by that rule, on every host, so FR-003 would be gutted. That draft
was built, measured going quietly green on a planted typo, and thrown away.

`gh` cannot settle it alone: a newer binary's field vocabulary is a superset of
an older one's, and nothing local says which supersets exist. So the tree says
which of *its own* fields it sends ahead of the field's arrival in `gh`, in
`factory/mergequeue/gh.py` next to the value it annotates:

```python
_VERSION_SENSITIVE_VIEW_FIELDS = frozenset({"baseRefOid"})
```

It names a **field**, not a `gh` release, so no version is pinned anywhere. It
is held to being a *strict subset* of `_VIEW_FIELDS` by a test that runs with no
`gh` at all, so it cannot drift into the second hand-maintained field list that
trap 5 forbids. And it is the only thing that can excuse a refusal: anything
outside it fails, on every host. Adding a name to it is an explicit claim that
the field is real and merely new.

Row (b) is US1-S4 happening for real: the check fails over to the degraded
verdict and **names the field**. Row (c) is the reason (b) is not an escape
hatch — one unvouched-for name in the same value and the whole thing is charged
to the argv again.

Note what `EXIT=4` in the SC-002 block below says about the spec's premise.
US1-S5 asserts that "`gh` validates field names before it authenticates".
**That is true on gh 2.98 and false on gh 2.45**: 2.45 checks authentication
first, so a bad field exits 4 — the acceptance code — and the fields are never
looked at. Classifying on the exit status alone therefore cannot see a bad field
on this host at all. The field set is settled a second way, against the
vocabulary `gh` itself declares through `gh __complete <command> --json ''`,
which exits 0 with no credential, no repository and no network, and gives the
same answer on both versions. Exit-status classification stays primary (FR-001);
this is the version-independent path to the fields specifically.

## SC-002 — the control: a check that denies everything is not an improvement

```
== T010 / SC-002: the control ==
$ GH_TOKEN= GH_CONFIG_DIR=<empty> gh pr view 1 --repo owner/repo --json state
To get started with GitHub CLI, please run:  gh auth login
Alternatively, populate the GH_TOKEN environment variable with a GitHub API authentication token.
EXIT=4
(exit 4 == _GH_EXIT_AUTH_REQUIRED 4: True)
_gh_would_refuse(['pr', 'view', '1', '--repo', 'owner/repo', '--json', 'state'])
  -> ACCEPTED (empty string)
$ GH_TOKEN= GH_CONFIG_DIR=<empty> gh auth status
You are not logged into any GitHub hosts. To log in, run: gh auth login
EXIT=1
_gh_would_refuse(['auth', 'status'])
  -> ACCEPTED (empty string)
_gh_would_refuse(['auth', 'status', '--ergane-test-unknown-flag'])
  -> REFUSED, charged to the argv: unknown flag: --ergane-test-unknown-flag
```

The `auth status` rows are the second half of the control, and the plan did not
anticipate them: `gh auth status` is the one command `GhClient` issues that `gh`
runs *without* a credential, and with none it exits **1** to report "not logged
into any GitHub hosts". A classifier that reads every non-zero exit but 4 as a
refusal denies that command — on gh 2.98 as much as on gh 2.45. It is kept as
acceptance by a narrow, named exception, and the exception is paired with a
`--help` parse probe so an unknown flag on the same command is still refused;
the last line above is that mutation control.

## SC-003 — no token, no repository, no network

```
== T011 / SC-003: no token, no git repository, no network ==
GH_TOKEN='' GITHUB_TOKEN='' GH_CONFIG_DIR=/tmp/ergane-gh-argv-contract-hnctulvz/gh-config (does not exist: True)
$ cd /tmp/ergane-gh-argv-contract-hnctulvz && git rev-parse --git-dir
fatal: not a git repository (or any parent up to mount point /)
Stopping at filesystem boundary (GIT_DISCOVERY_ACROSS_FILESYSTEM not set).
EXIT=128
all proxies -> http://127.0.0.1:1 (closed port): any request that escaped would fail
_gh_would_refuse(['pr', 'view', '1', '--json', 'erganeDefinitelyNotAJsonField'])
  -> REFUSED, charged to the argv: Unknown JSON field(s) erganeDefinitelyNotAJsonField: ...
_gh_would_refuse([... 'baseRefOid'])
  -> REFUSED, and this host is behind the tree: Unknown JSON field(s) baseRefOid: ...
```

Unsetting `GH_TOKEN` alone does not make a run credential-free — `gh` reads a
stored credential from its config directory — so the check now points
`GH_CONFIG_DIR` at a directory that does not exist. That is what makes the
authentication exit deterministic on a host where an operator has run
`gh auth login`, and it is why SC-002's control can assert `== 4` rather than
merely `!= 0`.

## The four environments, measured

The operator's requirement was one suite, green on a 2.45.0 host and on a
2.98.0 host, without shrinking `_VIEW_FIELDS` and without a version in a test.
There is no 2.98.0 on this machine, so the second environment is the one thing
here that is simulated — **and this says exactly how**. `/tmp/gh298/bin/gh` is a
shell script that `exec`s the real `/usr/bin/gh` for every call and changes one
thing: the vocabulary printed by `gh __complete … --json ''` gains `baseRefOid`.
Exit codes, flag parsing and auth behaviour are all the real binary's. It is not
a gh 2.98.0 and this does not claim to have run one; it is the single observable
difference that matters here, isolated.

`live-tier-skips-by-guard-not-marker` is about.

## What this story did not do

- **It did not shrink `_VIEW_FIELDS`** (trap 1). `baseRefOid` is 069-US1's free
  rebase and it is still sent.
- **It did not loosen `_run_json`** (trap 2), which was untouched.
- **It did not claim a gh 2.45.0 run it did not perform** (trap 10) — the
  opposite problem: the 2.45.0 runs are the real ones and the *newer* binary is
  the stub, described above.
- **It did not pin a `gh` version anywhere.** Grep the diff for `2.98`, `2.53`
  or `2.45` outside prose: there is nothing to find.

The residual, stated plainly: on a host whose `gh` lacks `baseRefOid`, this
suite cannot *prove* the poller would work there — it reports that it cannot,
by name. Turning that report into something an operator is told before an epic
parks, rather than something a skip line says, is 078-US2's capability probe.
