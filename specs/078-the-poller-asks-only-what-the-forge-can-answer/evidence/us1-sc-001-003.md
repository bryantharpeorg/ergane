## How the refusal was obtained (trap 10)

**From a `--json` field name no `gh` has, and — for `baseRefOid` — from the real
installed `gh`, which is old enough to refuse it.** No stub `gh` was put on
`PATH`, and nothing was simulated at the classifier boundary.

That is worth stating plainly, because the plan did not expect it. The plan
records `gh 2.98.0` measured at 07:12 CT and warns that no host would have a
`gh` old enough to refuse `baseRefOid`. This host does. It is the only `gh` on
the machine:

```

So `factory/mergequeue/gh.py:68 _VIEW_FIELDS` names a field the `gh` this
factory actually shells out to cannot answer. The landing poller is broken on
this host right now — the epic's premise, measured rather than suspected.

Note what the `EXIT=4` line above says about the spec's premise. US1-S5 asserts
that "`gh` validates field names before it authenticates". **That is true on gh
2.98 and false on gh 2.45**: 2.45 checks authentication first, so a bad field
exits 4 — the acceptance code — and the fields are never looked at. Classifying
on the exit status alone therefore cannot see a bad field on this host at all.
The field set is settled a second way, against the field vocabulary `gh` itself
declares through `gh __complete <command> --json ''`, which exits 0 with no
credential, no repository and no network, and gives the same answer on both
versions. Exit-status classification stays primary (FR-001); this is the
version-independent path to the fields specifically.

## SC-002 — the control: a check that denies everything is not an improvement

```
== T010 / SC-002: the control ==
$ GH_TOKEN= GH_CONFIG_DIR=<empty> gh pr view 1 --repo owner/repo --json state
To get started with GitHub CLI, please run:  gh auth login
Alternatively, populate the GH_TOKEN environment variable with a GitHub API authentication token.
EXIT=4
(exit 4 == _GH_EXIT_AUTH_REQUIRED 4: True)
_gh_would_refuse(['pr', 'view', '1', '--repo', 'owner/repo', '--json', 'state'])
  -> ACCEPTED (empty string)
$ GH_TOKEN= GH_CONFIG_DIR=<empty> gh auth status
You are not logged into any GitHub hosts. To log in, run: gh auth login
EXIT=1
_gh_would_refuse(['auth', 'status'])
  -> ACCEPTED (empty string)
_gh_would_refuse(['auth', 'status', '--ergane-test-unknown-flag'])
  -> REFUSED: unknown flag: --ergane-test-unknown-flag
```

The `auth status` rows are the second half of the control, and the plan did not
anticipate them: `gh auth status` is the one command `GhClient` issues that `gh`
runs *without* a credential, and with none it exits **1** to report "not logged
into any GitHub hosts". A classifier that reads every non-zero exit but 4 as a
refusal denies that command — on gh 2.98 as much as on gh 2.45. It is kept as
acceptance by a narrow, named exception, and the exception is paired with a
`--help` parse probe so an unknown flag on the same command is still refused;
the last line above is that mutation control.

  -> REFUSED: Unknown JSON field(s) baseRefOid: the installed gh (gh version 2.45.0 (2026-03-17 Ubuntu 2.45.0-1ubuntu0.3+esm3)) does not declare it for `gh pr view 7`
```

Unsetting `GH_TOKEN` alone does not make a run credential-free — `gh` reads a
stored credential from its config directory — so the check now points
`GH_CONFIG_DIR` at a directory that does not exist. That is what makes the
authentication exit deterministic on a host where an operator has run
`gh auth login`, and it is why SC-002's control can assert `== 4` rather than
merely `!= 0`.
