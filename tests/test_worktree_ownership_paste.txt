107 US1 — what git says about three directories, and the refusal that follows.

Run on 2026-08-25 against this branch's `factory/workgraph/worktree.py`, on git
2.43.0, in a scratch directory holding two `git init` repositories (`clone-a`,
`clone-b`) and one shared runtime root (`.ergane`). `ensure()` registered the
node worktree to clone-a; the probe then asked `_worktree_ownership` about three
directories and printed git's own two lines beside each answer.

Case 3 is the one to read twice. The directory is a bare `mkdir` with no `.git`
of any kind, and git still answers exit 0 with a legitimate top level and common
directory — clone-a's, because git walks *up* and the runtime root sits inside
the clone. Dispatched against clone-a, a check comparing only common directories
would call that owned and dispatch an agent into a directory that is not a
worktree at all. `--show-toplevel != the directory itself` is what refuses it.

That asymmetry is why the message names the owning clone rather than the
repository the epic was dispatched against. Nothing in the tree sweeps these
directories — `remove`, `reset` and `_archive_node` all shell
`git -C <target_repo> worktree remove`, which is the repo git has just refused —
so the operator's paste is the whole remedy, and the wrong one fails with an
error that names neither clone.

Reproduce: two `git init` repositories side by side, one `ensure(clone_a, ...)`
against a shared `factory_root`, then `ensure(clone_b, ...)`. The three cases and
both remedy outcomes are asserted in `tests/test_worktree_ownership.py`; the
scratch paths above differ per run and are the only thing that will not match.
